# Wireshark WASM

[Wireshark](https://www.wireshark.org)'s dissection engine compiled to
WebAssembly, served as an offline-capable PWA on GitHub Pages. Open a packet
capture — `pcap`, `pcapng` and dozens more formats — browse frames, the full
protocol tree, byte-level hex views, follow streams, conversations, endpoints,
I/O graphs and exportable objects. **Entirely in your browser**: no uploads, no
server-side processing, works offline after the first visit.

## How it works

- **Engine**: `wasm/engine/wiregasm.{js,wasm.gz,data.gz}` (~21 MB compressed)
  — [wiregasm](https://github.com/good-tools/wiregasm), which compiles
  Wireshark 4.6's `libwireshark` (epan, wiretap, wsutil + dissectors) to
  `wasm32-unknown-emscripten`. Published weekly from npm as
  `@goodtools/wiregasm`; the engine is GPL-2.0-or-later like Wireshark itself.
- **Execution**: the engine runs in a dedicated Web Worker
  (`src/engine-worker.js`). The page talks to it through a small seq-keyed RPC
  (`src/engine-client.js`); the worker fetches the `.gz` assets, inflates them
  with vendored pako and feeds them to the module via `wasmBinary` /
  `getPreloadedPackage` — the loader never issues its own network requests.
- **Dissection, not capture**: live capture (dumpcap/pthread) is impossible in
  a browser sandbox; this is the analyzer half of Wireshark — open a file,
  dissect, filter, follow, graph. That is what sharkd-based webshark does too.
- **Files never leave your device**: the capture is written into the
  engine's in-memory FS (`/uploads`) and dissected locally.

## File handling

When installed, the PWA doubles as a system-level handler for captures.
Everything is feature-detected; browsers without support keep the dropzone:

- **Open with** (desktop Chrome/Edge): `file_handlers` in
  `manifest.webmanifest` registers the app for 31 capture extensions
  (`.pcap`, `.pcapng`, `.snoop`, `.erf`, `.pcap.gz`, …);
  launched files arrive via `window.launchQueue` (and are re-stashed into
  OPFS so they survive a reload).
- **Share sheet** (Android Chrome): `share_target` receives shared files as a
  POST to `./__share`, which the service worker stashes in a dedicated cache;
  the app picks them up on the next load.
- **Native picker** (Chromium): "Native picker…" uses `showOpenFilePicker`.
- Everywhere else: drag & drop, or the classic file input.

## Offline / PWA

- `sw.js` precaches the app shell at install (tolerantly — a flaky fetch
  never kills the install) and serves everything same-origin cache-first.
- The 21 MB engine is deliberately **not** an install asset: it is cached
  through the normal fetch path on the first engine start, so the first load
  stays fast and every visit after that (online or not) has the engine.
- `build-info.json` is network-first: the About dialog shows the live build
  while offline still works.
- No COOP/COEP tricks are needed (the engine is single-threaded — no
  SharedArrayBuffer), so the site works from any static host as-is.
- Cache versions are content-hashed (`sw-manifest.js`, generated by CI), so a
  redeploy rotates caches cleanly instead of mutating the live one.

## How publishing works

`.github/workflows/publish.yml` runs **on every push to `main`**
(README/tests-only commits are ignored — they never reach the site), **every
Monday 04:17 UTC** (to pick up new wiregasm/Wireshark releases), and on
demand:

1. Resolves the latest `@goodtools/wiregasm` on npm (or the version you pass
   via `workflow_dispatch`), downloads and unpacks it into `wasm/engine/`
2. Smoke-tests the engine under Node
   (`.github/scripts/wasm-smoke-test.mjs`): boots it, dissects a synthetic
   pcap, exercises every API the site uses (frames, tree, filters, follow,
   taps, iograph, download)
3. Stages the site (repo files + engine + `build-info.json`), generates the
   versioned `sw-manifest.js`, and deploys to GitHub Pages

`workflow_dispatch` with `skip_build: true` redeploys the site using the
engine artifact from the most recent successful run (useful for shipping UI
fixes without re-downloading the engine).

## Repository layout

| Path | Purpose |
| --- | --- |
| `index.html` | UI (no frameworks, no external resources) |
| `src/app.js` | Application shell: packet list, tree, hex, statistics |
| `src/engine-worker.js` | The worker that owns the wiregasm module |
| `src/engine-client.js` | Promise-based RPC to the worker |
| `src/file-handling.js` | launchQueue / share target / pickers / drop |
| `sw.js`, `offline.html`, `manifest.webmanifest` | PWA / offline layer |
| `vendor/` | pako (inflate) + license |
| `icons/` | PWA icons (shark fin over a packet waveform) |
| `.github/workflows/publish.yml` | Weekly build & publish pipeline |
| `.github/scripts/` | wasm smoke test, sw-manifest generator |
| `wasm/` | Engine build output — **gitignored**; CI fetches it, drop local builds here for dev |
| `tests/` | Node test suites (`node tests/run-all.mjs`) |

## Local development

```sh
# put the engine in wasm/engine/ (npm pack @goodtools/wiregasm, copy
# dist/wiregasm.{js,wasm.gz,data.gz}), then:
python3 -m http.server -d . 8080
# open http://localhost:8080 — first engine boot downloads ~21 MB from this
# server (served with gzip already applied), afterwards it is cached
node tests/run-all.mjs   # static, SW, file-handling + engine integration
```
